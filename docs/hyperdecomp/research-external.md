Only public primary documentation, release metadata and papers were inspected. No target was executed, restricted component downloaded, dependency installed, source tree pulled or build changed. Scratcher's existing CPU path remains the baseline.

## DeepDi: what its speed claim actually means

The [USENIX Security 2022 paper](https://www.usenix.org/system/files/sec22-yu-sheng.pdf) describes superset instruction candidates, an instruction-flow graph, relational graph convolution and function-entry heuristics. It reports 146 KB/s single-core CPU throughput and 24.5 MB/s GPU throughput, with a 350× comparison against the paper's IDA Pro configuration. Its evaluated corpora include BAP, Windows LLVM 11 and SPEC; this is instruction identification/disassembly research, not an end-to-end decompilation benchmark. It neither proves 350× speedup on current hardware/software nor recovers absent/transformed original bytes by itself.

The [API](https://github.com/DeepBitsTechnology/DeepDi/blob/master/API.md) returns per-byte instruction-start probabilities, candidate lengths and function flags. All-byte candidates are a superset; the example applies a 0.5 probability threshold. Scores must remain candidate evidence rather than definitive coverage. Batch sizing trades overhead against VRAM pressure, and completion requires synchronization. The [GPU container](https://github.com/DeepBitsTechnology/DeepDi/blob/master/Dockerfile-gpu) pins Ubuntu 20.04, CUDA 11.4.3/cuDNN 8 and ONNX Runtime GPU 1.10.0. Native Windows core compatibility was not established by the `.so` delivery or Windows driver requirement.

**Proposed experiment, not implemented:** persistent external instance, deterministic byte/range input and batch IDs, output offset/length/score records, then independent decoder validation, overlap resolution and metadata/control-flow corroboration. Measure model startup, parsing, transfer, inference, synchronization and validation separately. Preserve CPU fallback and compare precision/recall on labeled readable fixtures before counting any new candidates.

## angr and RetDec as analysis oracles

angr exposes lifting, CFG/VSA/data dependencies, symbolic execution and decompilation through [Python libraries](https://github.com/angr/angr). Its [IR documentation](https://api.angr.io/en/stable/advanced-topics/ir.html) explains shared analyses across x86, ARM, MIPS and PowerPC via VEX. These are architectural capabilities, not a promise that every lifter implements every extension or that all targets decompile equally well.

Its [CFG documentation](https://docs.angr.io/en/latest/analyses/cfg.html) distinguishes static `CFGFast` from stateful emulation. CFGFast accepts supplied function starts and attempts indirect jump resolution; complete code scanning can be disabled for mixed code/data blobs. For a fair Scratcher comparison, fix input bytes, mappings, starts, scan policy and budgets. Request bounded static work first; symbolic exploration is a separate cost and the [FAQ](https://docs.angr.io/en/latest/faq.html) explicitly discusses state explosion. GPU acceleration is not established for angr's full pipeline by these sources.

RetDec's library entry points are described by its [5.0 release](https://github.com/avast/retdec/releases/tag/v5.0), including `src/retdectool` and the decompiler executable as examples. **Inference:** first use a separately installed executable/worker to avoid coupling Scratcher to RetDec's LLVM/dependency versions, global state and allocation behavior. Only consider an embedded library after API/thread-safety, selected-range semantics, cancellation and memory tests. No current numeric speed advantage was established, and decompiler output must be tested for types/control-flow semantics, not merely whether text was returned.

## GPU graph and dataflow options

[Gunrock's current documentation](https://github.com/gunrock/gunrock) describes frontier-oriented CUDA/C++ graph operations under Apache-2.0, C++17/CMake >=3.24 and CUDA >=12.4 or ROCm/HIP >=6.4. It lists MSVC support, but that is not a verified Windows build here. **Inference:** reachability, edge filtering, prefix/compaction and large graph iterations may fit; sparse small per-function CFGs may lose to transfer/launch costs. Branch semantics, alias reasoning and lifting still need an analysis model. Keep a resident compact graph and benchmark identical results including transfer and construction.

[GraphBLAST](https://github.com/gunrock/graphblast) offers Apache-2.0 GraphBLAS-style GPU primitives. Its listed tested CUDA/compiler stack is much older (CUDA 9.1/9.2, GCC 4.9/5.4). Treat it as an algorithm/reference option requiring a compatibility spike, not the default dependency. Neither graph library supplies SSA, a decompiler or correct transfer functions automatically.

The [GPUlog/GDlog paper](https://arxiv.org/abs/2311.02206) reports up to **45×** versus Soufflé on context-sensitive `httpd` points-to queries; this is scoped relational analysis, not all binary analysis. The [GDlog artifact](https://github.com/harp-lab/gdlog) requires CUDA >=11.4.2 and says the complete transitive-closure benchmark needs an A100 with at least 40 GB VRAM; smaller devices may run out of memory. [Code is MIT](https://github.com/harp-lab/gdlog/blob/main/LICENSE), but no packaged production release was established. Its instructions mention an old Thrust overflow patch: do not apply that blindly to modern CCCL.

[VFLog's 2025 paper](https://arxiv.org/abs/2501.13051) reports >200× over CPU column-oriented engines and 2.5× over compared GPU engines on selected workloads. The [artifact](https://github.com/harp-lab/vflog) lists NVIDIA HPC SDK >=24.1, OpenMP, oneTBB and CMake >=3.20. No repository license was identified by this review/API; public visibility alone does not grant copying/redistribution rights. Use the paper's ideas, withhold code incorporation until license is established.

[SRDatalog, April 2026](https://arxiv.org/abs/2604.20073v2), targets worst-case-optimal multiway joins, columnar storage and deterministic allocation to address join blowup. It reports **21×–47× geometric-mean** speedups on its program-analysis workloads. The [associated active Python/C++/CUDA project](https://github.com/harp-lab/srdatalog-python) has an [MIT license](https://github.com/harp-lab/srdatalog-python/blob/main/LICENSE); its generated-shared-library workflow still needs Windows/toolchain, semantic and cancellation validation. Paper and current repository must be pinned separately; no local reproduction occurred.

**Proposed first dataflow experiment:** encode a small explicit monotone relation/bitset analysis with identical CPU and GPU semantics; compare fixed-point facts exactly, including cycles, empty graphs, skew, overflow and exhausted VRAM. Measure rule compilation, data upload, iteration, deduplication and readback. General SSA type propagation, heap aliasing and rich decompilation remain separate requirements. These papers justify research into specific relational kernels; their headline speedups cannot be multiplied or transferred to Scratcher's end-to-end runtime.

## Concrete decision boundary

Implement dependency-neutral records and an optional backend boundary first. Retain native CPU loading, decoding and analysis as reference/fallback; report backend availability explicitly. Gate each accelerator on measured input size and a validated result contract. DeepDi needs verified commercial/distribution terms and an actual working key; angr needs a pinned environment and full dependency-license inventory; RetDec needs an isolated compatibility test; GPU research needs legal source availability and VRAM/Windows validation. All integrations above remain **not implemented and not benchmarked locally** in this research change.

Release checks used primary GitHub API `repos/<owner>/<repo>/releases/latest` for DeepDi, RetDec and Gunrock and PyPI JSON for angr; repository activity/licensing metadata was cross-checked with the linked source pages. Mutable `master`/`main` documents were inspected on the retrieval date and must be commit-pinned before implementation. The unavailable DeepDi agreement and unidentified VFLog license are explicit unresolved items.
